# 出站内容守卫

## 什么时候用

任何**把内容发到本机之外**的动作之前：

- 推送到公开仓库（尤其是 `public` 的个人技能仓 / 工具仓）
- 发布站点、生成对外分享链接
- 导出交付包、上传云盘、发给第三方
- 已经在推、想确认「推出去的那批里有没有机器痕迹」

**不需要**：纯本地提交、内容本来就只在本机流转。

## 两级严重度（先把口径定死）

不把严重度分开，就会被一堆 WARN 淹没真信号 —— 而真信号（主目录路径 + 用户名）恰恰是**隐私**。

| 命中形态 | 级别 | 处置 |
| --- | --- | --- |
| **本机主目录路径**：`C:\Users\<名>\…`、`/home/<名>/…`、`/Users/<名>/…` | **FAIL，阻断** | 必须脱敏后再发布。它连**用户名**一起暴露 |
| **本机盘符路径**：`E:\…`、`D:\…`（不含用户名） | **WARN** | 若该路径已在出站清单/白名单登记，可放行；否则建议改成相对路径或占位符 |
| 已掩码形态：`<用户名>`、`…`、`<工作区根>` | — | 通过 |
| **凭据字面量**：`sk-`、`ghp_`、`AKIA` 等 | **FAIL，阻断** | 交给凭据泄露应急流程（见下「分工」） |

> ⚠️ **已登记的 WARN 不算失败**：把它写进报告、如实列出，而不是为了「全绿」去改判据或删记录。
> 反过来，**FAIL 不能用「这条是历史条目」来豁免** —— 隐私泄漏与条目新旧无关。

## 四条铁律

1. **扫描发生在发布之前，且扫的是「实际会推送的那个集合」。**
   扫整个工作区会把`tmp/`、备份、历史归档全捞进来，噪声淹没信号；而且它们**根本不会出站**。
   正解：先让出站工具 dry-run 给出待推清单，再**对这个清单**逐项扫内容。

2. **先 dry-run 拿清单，再 apply。**
   出站工具默认应是 dry-run。清单 = 「会推哪些文件 + 两个通道各几项」，这才是权威口径；
   不要凭「我改了哪些文件」自己推断。

3. ⭐ **泄露一旦进了提交，新提交盖不住历史 —— 只有 `amend` 一条路。**
   再补一次「脱敏后的提交」或 `git revert`，都只是把真路径**再写进历史一次**，原提交里那份**原封不动**。
   所以「已经提交了」这个事实，直接把处置从「改文件」变成「改提交」。

4. ⭐ **核实要读「已提交的 blob」，不是工作区文件。**
   工作树干净 ≠ 提交里干净。实测过的形态：工作区的文件**早已脱敏**，而 `HEAD` 里的 blob
   **仍含真路径**（脱敏发生在上一次提交之后）。读工作区会得出**假绿**。

## 已提交泄露的补救：amend 七步

1. **备份 + 记 pre-amend sha**（可回滚的凭据）。
2. **脱敏**：把真路径换成占位符（见下节）。别只替换一处 —— 用「出现位置全量列一遍」的方式确认清零。
3. `git add -- <只这一个文件>`（**绝不** `git add -A`，防连带别人的产物）。
4. **守卫**：staged 集合必须**恰等于**期望集合。
5. `git commit --amend`（保留原提交标题；需要改信息就一并改）。
6. **回读断言**：`git show HEAD:<path>`（或 `git cat-file -p HEAD:<path>`）里，命中数必须归 **0**。
   —— 注意读的是 **HEAD 的 blob**，不是工作区文件。
7. **复核远端基线未动**：amend 改的是本地提交，远端 ref 应当还在原处，别把「远端还是旧的」误读成失败（那正是推送前的正常状态）。

> push 侧与验收侧的机制守卫（staged 集合、行尾归一、远端 sha 对账、验收器输入契约）见 `guarded-git-commit-mixed-repo`，本技能不重复。

## 占位符怎么写

| 原形态 | 换成 | 说明 |
| --- | --- | --- |
| `C:\Users\<名>\…` | `<本机主目录>\…` 或直接相对化 | 关键是**连用户名一起去掉** |
| 工作区根的绝对路径 | `<工作区根>` | 文档里描述操作时读起来更清楚 |
| 桌面下的目录 | `Desktop\<目录>\` 或 `<某工作区外目录>\` | 保留「曾在工作区外」这一事实，隐去机器相关部分 |

**原则**：脱敏**不改语义**。读的人仍应知道「这里曾是一个工作区外的归档根」，只是不该知道**是哪台机器的哪个用户**。

## 历史留痕该不该动？

判据是「它会**被读取成真实路径**吗」，不是「它看起来像不像路径」：

| 形态 | 处置 |
| --- | --- |
| 会被程序/人照着**执行或解析**（技能手册的路径口径、脚本常量、计划文件的交付物字段） | **活引用 ⇒ 必须改** |
| 只是在**记录**「当时发生了什么」（变更日志、台账、审计报告、证据快照） | **历史留痕 ⇒ 不该改语义**；但命中 **FAIL 级**（主目录路径）仍须脱敏 |

跨目录批量处理时，先把**旧路径的引用点全集** grep 出来再分类 —— 漏一个活引用就留下悬空路径。
（迁移类任务里这套「引用点全集 + 改判据调用方」的完整做法见 `falsifiable-file-migration`。）

## 与相邻技能的分工

| 技能 | 管什么 | 不重复的点 |
| --- | --- | --- |
| **本技能** | **内容层**的「机器环境泄漏」（本机路径 / 用户名）在**发布前**的拦截与补救 | —— |
| `guarded-git-commit-mixed-repo` | 提交 / 推送的**机制**守卫（staged 集合、行尾归一、远端 sha 对账、验收器契约） | 它不管内容里写了什么 |
| `secret-leak-response` | **凭据**（Key / Token / 密码）泄露的应急响应（扫描 / 轮换 / 实测吊销） | 凭据是「动作级」风险（要吊销），路径是「隐私级」风险（要脱敏） |

## 反模式（踩过的）

- ❌ **只扫工作区、不扫已提交内容** —— 得到假绿（工作树干净并不代表提交干净）。
- ❌ 发现泄露已提交，就**再补一个脱敏提交** —— 原提交里那份真路径**还在历史里**。
- ❌ 只 `git show` 工作区文件来「确认已脱敏」—— 核实的对象错了。
- ❌ 把「推出去发现路径」当成小事儿、只在下次注意 —— **已经出去了**，要按 amend 补救。
- ❌ 为消掉 WARN 级命中去删历史记录条目 —— 那是**改历史**；WARN 如实登记即可。
- ❌ 把 `tmp/`、备份、历史归档一起扫，然后被几千条命中吓得改判据 —— 先按「实际会推送的集合」缩小扫描面。

## 参考实现

`scripts/scan_outbound_paths.py` —— 对给定文件（或目录）做**分级**扫描：
`FAIL` 级（本机主目录路径 / 凭据前缀）与 `WARN` 级（本机盘符路径）分开报，并给出**行号 + 掩码后的命中片段**
（不回显完整真路径）。

带 `--selftest`，且夹具**同时**包含：真正的 FAIL 样本、真正的 WARN 样本、**已掩码形态**（必须判「通过」）、
以及**看起来像路径但其实是相对路径**的样本（必须判「通过」）。四类都在，才说明判据**既不漏也不误**。
